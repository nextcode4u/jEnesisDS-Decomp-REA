# jEnesisDS BlocksDS Port C

The port compiles the project's ARM7 and ARM9 programs from C with Wonderful's compiler. It links against libnds and uses the standard BlocksDS startup code. The C core runs the 68000 and VDP diagnostic, boots Sonic the Hedgehog into Green Hill Zone Act 1, and starts Sonic the Hedgehog 2 in one-player Emerald Hill Zone Act 1 in melonDS. The touch menu provides two save slots. Cartridge games with battery-backed SRAM can also use their in-game save menus. The C Z80 executes Genesis sound drivers and handles YM2612 timer status. ARM7 mixes six-channel YM2612 FM, DAC samples, and PSG audio. YM2612 accuracy, broader game compatibility, and sustained full-speed emulation remain open.

## Build on Linux or WSL

Install Python 3, GNU Make, and the `blocksds-toolchain` package from Wonderful Toolchain. The C target was tested with BlocksDS 1.25.0. [BlocksDS Linux installation guide](https://blocksds.skylyrac.net/docs/setup/linux/)

From the repository root, run:

```sh
make
```

This compiles and links both CPUs into ELFs under `build/c/`, then packages them into `build/jEnesisDS-C.nds`. The fresh build requires only this checkout and the installed SDK and toolchain. Set `WONDERFUL_TOOLCHAIN` or `BLOCKSDS` to use a custom installation.

In melonDS, enable a virtual DLDI SD card and add Genesis ROMs to it. The bottom screen uses the original jEnesisDS menu artwork and font. The build converts the editable tile sheets, palettes, and tilemap into C. The footer shows the port's measured Genesis frames per second during gameplay.

- In the ROM browser, use **Up** and **Down** to highlight an entry, **Left** and **Right** to change pages, **A** to open or run the selection, and **B** to open the parent folder.
- During emulation, touch the panel to pause and touch again or press **SELECT** to resume. Press **SELECT** while running or tap the cartridge icon to open the browser. Press **SELECT** in the browser to return to the current cartridge.
- Tap the controller icon to open configuration. Use **A** or tap **Country** to cycle the region for the next cartridge. European cartridges target the PAL refresh rate of about 50 Hz. Select the **Controller** row to switch between 3-button and 6-button modes. In 6-button mode, DS **X**, **L**, and **R** send Genesis **X**, **Y**, and **Z**. Hold **L + R + Start** for Genesis **Mode**.
- Tap **[1]** or **[2]**, choose **SAVE** or **LOAD** with the D-pad, and press **A**. The portable C build's versioned `.jsc` files live next to the cartridge. Games with header-declared parallel SRAM use a separate `.srm` file named after the ROM. Older C-port states preserve the cartridge's current SRAM when loaded.

## C sources

- [ROM browser](source/main.c) mounts the SD card through libnds and browses directories using standard file APIs.
- [Bottom-screen interface](source/frontend.c) loads the [recovered menu assets](assets/frontend) into libnds tiled backgrounds and draws the browser, status panel and state slot indicators.
- [ARM7 services](source/arm7/main.c) set up the system FIFO for storage and send input samples to the ARM9.
- [Cartridge loader](source/cartridge.c) reads raw ROMs, decodes SMD blocks, parses the cartridge header and its SRAM range, and computes the Genesis checksum.
- [68000 interpreter](source/m68k.c) reads the reset vectors, runs the supported instructions, handles interrupts, batches repeatable work-RAM loops, and reports the address and opcode where unsupported work stops execution.
- [Genesis bus and VDP](source/megadrive.c) map the cartridge and mirrored RAM, handle three-button and six-button input and Z80 bus requests, schedule vertical and horizontal interrupts, map cartridge SRAM, and access VRAM, CRAM, and VSRAM through the VDP.
- [Z80 bus and timing](source/z80_bus.c) runs the [MIT-licensed C Z80](source/third_party/z80), synchronizes it with the 68000, and delivers the VBlank interrupt pulse. The shared bus exposes YM2612 register and timer status to both guest processors.
- [DS renderer](source/vdp_ds.c) uses tiled backgrounds and hardware sprites for supported modes. It can present interlace mode 2 field by field and switch Plane A maps and sprite tables partway through the frame. It also draws Genesis window rows that cover the full viewport width. For 128-column planes, it maps the visible area into one or two 64-column DS tile maps and switches maps between scanlines. The [bitmap renderer](source/vdp_render.c) handles layouts outside the DS tile, map, or sprite limits. During HBlank, DMA streams the DS scroll registers for each scanline. Raster interrupts handle map and layer changes. Both renderers use recorded per-line vertical scroll when the guest changes it during active display. Both renderers center the viewport on the Genesis picture. The bitmap renderer indexes each scanline’s sprites in hardware evaluation order. It composes visible spans in cached RAM and uploads the completed page with DS DMA.
- [Save states](source/savestate.c) serialize the emulated hardware state, verify the cartridge identity, and reject invalid files before restoring the running state. Cartridge SRAM data is flushed on pause, when switching games, and periodically during play.
- The [PSG mixer](source/arm7/psg.c) synthesizes tone and noise on the ARM7. When every channel is muted, it advances the oscillator counters and noise state for the entire block together. The [YM2612 event capture](source/dac.c) records timed 68000 and Z80 writes. The [FM synthesizer](source/arm7/fm.c) renders six independent PCM voices at the original nominal rate of 27,563 Hz. Each voice plays through two DS hardware mixer channels using the original volume and pan settings.

The C ROM booted in melonDS 1.1 and loaded Sonic the Hedgehog in both BIN and SMD formats from a subdirectory on the virtual SD card. A host check verified that the loader decoded a cartridge from BIN and SMD into identical bytes and rejected truncated and invalid files.

The C build runs the Genesis backdrop diagnostic in melonDS 1.1. Both captured top-screen colors match the original jEnesisDS 0.7.4 frames pixel for pixel. Sonic's intro, title screen, movement, jumping, and both save slots were tested in melonDS. A restored Green Hill Zone frame matched the frame at the time of saving and matched across both renderers. A separate PSG diagnostic produced audio and muted when paused. melonDS showed both fields in an interlace diagnostic and the separate views in Sonic 2’s split-screen demo. A live Sonic 2 two-player race also draws both views. The tile renderer keeps HBlank interrupts armed across adjacent scanline changes so that the separator can blank one line and the lower viewport can immediately restore the layers. A horizontal-interrupt diagnostic switched vertical scroll partway through the image in both renderers. The VDP still uses synchronous DMA and samples tile data and palettes at frame granularity. PSG registers are sent to the mixer at frame granularity. Run `make check` for host checks covering the CPU, idle-loop scheduling, controller handshakes, Z80 execution and bus access, YM2612 timers, frequency latches, and DAC write timing, VDP interrupts, DMA and port readback, interlaced rendering, scanline scroll and layout changes, tile and sprite priority, save-file validation, and FM and PSG synthesis.

The original and BlocksDS browsers produced pixel-identical captures in melonDS with the same ROM listing. Green Hill Zone spot checks showed about 28–40 guest frames per second in DS mode. In melonDS 1.1, replaying the first 80 guest frames from the same Sonic 2 split-screen save improved from 10.3 to 14.1 guest FPS. Average guest CPU time fell from 2.14 million to 1.70 million DS timer ticks per guest frame, and bitmap drawing fell from 2.08 million to 1.28 million ticks per draw. A subsequent pass on CPU shifts and sound mixing measured 14.2 guest FPS on the same replay. Indexing the sprites by scanline and packing the output four pixels at a time raised the same replay to 14.7 guest FPS and cut average drawing time from 1.28 million to 1.12 million ticks. Separating the larger opcode handlers from the dispatcher and caching the next Z80 sync deadline raised the replay to 15.8 guest FPS. Guest CPU time fell from 1.69 million to 1.54 million ticks per frame. The split-screen hardware path raised the same replay from 15.8 to 19.9 guest FPS and reduced drawing from about 1.10 million to 94,477 ticks per draw. A fixed-frame melonDS capture matched the bitmap output pixel for pixel. With video rendering disabled, the 68000 and sound emulation averaged about 1.59 million ticks per frame, including about 384,000 ticks in Z80 synchronization. With the faster 68000 paths, Z80 polling and VRAM DMA, the same replay reached 26.7 guest FPS and averaged 1.20 million CPU ticks per frame. The CPU and timed FM/DAC traces matched the earlier build across the 240-frame replay and in the 16-cartridge host run. Sustained NTSC full speed requires about 560,000 ticks per frame for the whole workload.

Scroll DMA, faster Z80 pulse handling, and 68000 fetch and instruction changes improved the Sonic 2 split-screen replay. ARM9 now stores cartridge ROM and 68000 work RAM in its native word order. Byte accesses, Z80 reads, VDP transfers, and save states still use the guest address order. The table shows guest FPS over the same 600 frames in melonDS 1.1 with the full-rate FM mixer enabled. The port uses 134 MHz in native DSi mode. The Z80 now builds arithmetic and logic flags together in the F register.

The tile renderer stores the two map pages in VRAM bank E and caches both interlace fields per page in bank A. It uploads tile rows as 32-bit words. The frame scheduler retains overdue guest frames between batches and polls input after at most two. On the same replay, the DS result reached 30.0 guest FPS and native DSi reached 57.5. DSi draw time fell from 84,271 to 48,087 ticks per draw. The host pacing test covers overdue frames, the queue bound, pause, and the PAL rate.

In the live Sonic 2 two-player race, the BlocksDS C build draws both views. Direct cartridge opcode fetches and paired RAM accesses reduce interpreter work while retaining the guest bus order. Over the same 600 guest frames in melonDS 1.1, the byte-matched devkitARM r20 build took 600 VBlanks. The BlocksDS C build took 600 VBlanks in native DSi mode and 973 VBlanks in DS mode, equivalent to 59.83 and 36.89 guest FPS. The input script holds Right during the live race. The saved-demo measurements above use a separate fixture.

The NTSC frame budget for CPU and rendering together is about 560,000 ticks. In a separately instrumented DS run, Z80 synchronization and execution accounted for about 314,000 ticks per guest frame. Captures of both interlace fields, the 128-column intro, and the final replay frame matched pixel for pixel across the performance passes. The 600-frame state and timed audio trace and the 16-cartridge host run also matched. The memory-layout host check covers odd ROM sizes, mirrored RAM, Z80 ROM reads, and VDP DMA, and compares the save files from both layouts byte for byte.

For the first 240 guest frames of Earthworm Jim in melonDS 1.1, hardware window rendering reduced average draw time from about 567,000 to 30,000 ticks. The capture on guest frame 240 matched the bitmap renderer pixel for pixel. Batching the 68000 work-RAM wait loop through the existing Z80 checkpoints increased startup speed from 12.9 to 18.7 guest FPS.

For Sonic 2's 128-column layouts, the tile renderer handled 289 of the 309 wide-map frames in a scripted 1,400-frame boot and demo run. The DS tile model matched the bitmap renderer on all 289 frames. A melonDS capture of the SEGA intro using two map origins also matched the bitmap output pixel for pixel.

The save slot restored Sonic's earlier position and timer. A host smoke run advanced 16 locally available cartridges through 1,400 frames each with scripted Start presses and no interpreter stop. The set included Sonic 1–3, both Earthworm Jim games, both Shining Force games, Comix Zone, Contra Hard Corps, and Golden Axe II. A separate melonDS run reached the Sonic 3 title screen. An SRAM diagnostic persisted its test value across a full melonDS restart. The host checks cover CPU execution and leave graphical and audio compatibility to runtime testing.

A DAC-only cartridge test in melonDS 1.1 produced audio with the DAC enabled and silence with the DAC disabled or the menu open. A six-voice FM diagnostic played all four operators on every channel, and the mixer muted when the browser opened. An instrumented run with PSG muted reduced ARM7 mixing time from about 56,400 to 41,400 timer ticks per 48-sample block. The 120-block sample recorded zero late buffers after the change. The mixed FM and PSG test recorded late buffers with 48-sample blocks. Increasing the block to 64 samples preserved the output rate and produced zero late buffers in a 120-block mixed-audio sample. Sonic also restored an existing C-port save after the audio change. C-port saves track YM2612 registers, held notes, and committed frequencies. The normal frequency latch is shared across both banks and channel 3 has a separate latch, matching the original write handler. The mixer reconstructs notes on load. Older states recover their pitches from the saved register image. The save format does not capture live oscillator phase or envelope position. The current FM mixer uses 128-sample hardware buffers and renders spans at the timed register-write boundaries.

The FM comparison ran the original 0.7.4 ARM7 mixer directly with controlled YM2612 register writes. Across all eight algorithms, enabling register `22h` and the AM bits left the original PCM unchanged. The port now matches that behavior. It also reproduces the original FM stereo routing and per-side gain. A patch with zero decay rate enters sustain when the sustain level is zero, as it does in the original. The host checks cover the original PCM hashes for all eight algorithms, three feedback levels, variable block lengths, and muted-operator transitions.

Replaying the same timed YM2612 register writes and render spans for 1,400 Sonic 2 frames through both cores matched all 3,869,784 PCM words across the six voices. All 396 randomized cases that ran to completion in the reference matched. Four additional cases faulted when running the original ARM7 code in the reference harness. The comparison ends at per-voice PCM. Audio timing in a whole-game run still depends on the two builds' register delivery and buffer scheduling.
